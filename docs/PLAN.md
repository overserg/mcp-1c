# План: MCP-сервер для 1С:Предприятие 8.3

## 1. Цель

MCP-сервер, через который агент (Claude Code) может:

1. **Изучать конфигурацию** — объекты метаданных, их структуру, модули, формы, права.
2. **Находить связи** между объектами — кто ссылается на справочник, какие регистры двигает документ, где вызывается процедура общего модуля.
3. **Выполнять запросы к базе** (язык запросов 1С) — получать данные для тестов.
4. **Проверять внесённые доработки** — синтаксический контроль модулей, движения документов, журнал регистрации, выполнение тестов.

## 2. Архитектура: два канала доступа

```
Claude Code ──stdio/HTTP (MCP)──► mcp-1c (Python)
                                   │
                ┌──────────────────┴───────────────────┐
                ▼                                      ▼
   A. Offline-индекс метаданных            B. Live-коннектор к базе
   (выгрузка конфигурации в XML/EDT)       (расширение 1С с HTTP-сервисом)
   • парсинг XML → SQLite                  • запросы (Запрос.Выполнить)
   • граф связей, FTS по коду BSL          • чтение объектов, движений
   • работает без запущенной 1С            • журнал регистрации
                                           • (опц.) код в безопасном режиме
                ▼
   C. Пакетный режим конфигуратора (1cv8 DESIGNER / ibcmd)
   • DumpConfigToFiles, CheckModules, CheckConfig, запуск тестов
```

### Почему так

| Способ | Плюсы | Минусы | Решение |
|---|---|---|---|
| Выгрузка в XML (`/DumpConfigToFiles`) или исходники EDT | Полная структура + весь код, быстро, не нужна живая база | Не видит данные | **Основа для метаданных и связей** |
| HTTP-сервис в расширении (.cfe) | Кроссплатформенно, произвольные запросы, не меняет основную конфигурацию | Нужна публикация (Apache/IIS или автономный сервер `ibsrv`) | **Основа для данных** |
| OData (стандартный интерфейс) | Без доработок | Нет произвольных запросов, ограниченная модель | Не используем (опционально) |
| COM (`V83.COMConnector`) | Без публикации | Только Windows, тяжёлые процессы, утечки | Запасной вариант |

## 3. Инструменты MCP (tools)

### 3.1 Метаданные (offline-индекс)
| Tool | Назначение |
|---|---|
| `list_objects(type?, filter?)` | Список объектов: Справочники, Документы, Регистры, ОбщиеМодули и т.д. |
| `get_object(name)` | Структура: реквизиты (с типами), ТЧ, формы, команды, макеты, свойства (иерархия, нумерация, проведение…) |
| `get_module(object, kind)` | Текст модуля (объекта, менеджера, формы, общего) |
| `list_procedures(module)` / `get_procedure(module, name)` | Процедуры/функции с `Экспорт`, директивами компиляции, параметрами |
| `search_code(pattern, scope?)` | Полнотекстовый/regex-поиск по BSL |
| `get_subsystems()` | Дерево подсистем и состав |
| `get_role_rights(role | object)` | Права ролей на объект |
| `get_event_subscriptions()`, `get_scheduled_jobs()` | Подписки и регл. задания с обработчиками |

### 3.2 Связи (граф в SQLite)
| Tool | Назначение |
|---|---|
| `find_references(object)` | Где используется тип объекта: реквизиты, измерения регистров, определяемые типы, ПВХ, параметры, подписки, роли, код |
| `get_register_links(document)` | Какие регистры двигает документ (`Движения`) и какие документы являются регистраторами регистра |
| `find_callers(module.method)` / `find_callees` | Граф вызовов по коду BSL |
| `get_dependency_graph(object, depth)` | Подграф связей в виде Mermaid / JSON |
| `diff_configs(dump_a, dump_b)` | Что изменилось между двумя выгрузками (для проверки доработки) |

Типы рёбер графа: `attribute_type`, `tabular_attribute_type`, `register_dimension`, `register_recorder`, `based_on`, `defined_type`, `subsystem_member`, `role_right`, `event_subscription`, `scheduled_job`, `functional_option`, `code_call`, `code_reference` (например `Справочники.Номенклатура`).

### 3.3 Данные (live через HTTP-сервис)
| Tool | Назначение |
|---|---|
| `execute_query(text, params?, limit=100)` | Выполнить запрос 1С; авто-`ПЕРВЫЕ N`, таймаут, результат таблицей (JSON/Markdown) |
| `validate_query(text)` | Проверка синтаксиса запроса без выполнения |
| `get_object_data(ref | type+code/number)` | Реквизиты и ТЧ конкретного объекта |
| `get_document_movements(ref)` | Движения документа по всем регистрам |
| `get_register_balances(register, date?, filter?)` | Остатки/обороты |
| `get_event_log(from, to, level?, event?)` | Журнал регистрации — ошибки после изменений |
| `get_runtime_metadata()` | Метаданные живой базы (сверка с индексом, учёт расширений) |
| `eval_code(code)` **(выключено по умолчанию)** | Выполнение кода в `УстановитьБезопасныйРежим(Истина)`, только на тестовой базе |

### 3.4 Проверка доработок (пакетный режим)
| Tool | Назначение |
|---|---|
| `check_modules(modes)` | `DESIGNER /CheckModules -ThinClient -Server …` — синтаксический контроль |
| `check_config()` | `/CheckConfig` — расширенная проверка |
| `refresh_index()` | Перевыгрузка конфигурации (`/DumpConfigToFiles -update` — инкрементально) и переиндексация |
| `run_tests(suite?)` | Запуск YAxUnit / Vanessa-ADD и возврат отчёта (JUnit) |
| `snapshot_query` / `compare_snapshot` | Сохранить результат запроса «до» и сравнить «после» доработки |

### 3.5 Resources и Prompts
- Resources: `1c://metadata/{Тип}/{Имя}`, `1c://module/{...}` — чтобы агент мог прикреплять объекты как контекст.
- Prompts: «Изучить объект», «Проверить доработку документа», «Подготовить тестовые данные».

## 4. Безопасность

- **Только тестовые/копийные базы.** В конфиге явный флаг `environment: test`; без него live-инструменты не включаются.
- Отдельный пользователь 1С с ролью только на чтение + право на HTTP-сервис.
- В HTTP-сервисе запрос выполняется в транзакции с откатом / только `ВЫБРАТЬ`; отклонение `ПОМЕСТИТЬ` в постоянные таблицы не нужно (в 1С его нет), но блокируем вызовы с записью в `eval_code`.
- Лимиты: строк в ответе, размера ответа, таймаут запроса.
- `eval_code` — по отдельному флагу, безопасный режим, логирование.
- Аудит: все запросы агента пишутся в локальный лог.
- Маскирование персональных данных (опционально, по списку реквизитов).

## 5. Технологический стек

- **MCP-сервер:** Python 3.11+, официальный `mcp` SDK (FastMCP), транспорт stdio (для Claude Code) + опционально Streamable HTTP.
- **Парсинг выгрузки:** `lxml`; поддержка формата конфигуратора (XML) и EDT (`.mdo`).
- **Индекс:** SQLite + FTS5 (объекты, реквизиты, рёбра графа, код).
- **Парсер BSL:** на первом этапе regex-лексер (процедуры, вызовы `Модуль.Метод`, обращения `Справочники.X`); позже — tree-sitter-bsl.
- **HTTP-клиент:** `httpx`, Basic-auth.
- **Расширение 1С:** `MCPConnector.cfe`, исходники в репозитории (XML-выгрузка расширения), HTTP-сервис `/hs/mcp/v1/*`.
- **Тесты:** `pytest` на фикстурах-выгрузках (маленькая демо-конфигурация), мок HTTP-сервиса.

## 7. Этапы

### Этап 0. Уточнение окружения (1–2 дня)
- ОС сервера 1С и рабочего места (Windows/Linux), версия платформы 8.3.x.
- Файловая или клиент-серверная база; есть ли веб-публикация.
- Конфигуратор или EDT; типовая (на БСП) или самописная.
- Подготовить тестовую базу + выгрузку конфигурации для фикстур.

### Этап 1. MVP: метаданные offline (≈1 неделя)
- Каркас MCP-сервера, конфиг, логирование.
- Парсер `Configuration.xml` и объектов (Справочники, Документы, Регистры, Перечисления, ОбщиеМодули, Константы, Обработки, Отчёты).
- Индекс SQLite; tools: `list_objects`, `get_object`, `get_module`, `search_code`, `list_procedures`, `get_procedure`.
- Подключение к Claude Code (`claude mcp add 1c -- mcp-1c --config ...`).
- **Критерий готовности:** агент отвечает «какие реквизиты у документа X и что делает его ОбработкаПроведения».

### Этап 2. Связи (≈1 неделя)
- Граф рёбер из метаданных (типы, регистраторы, подписки, роли, подсистемы, определяемые типы).
- Извлечение вызовов и обращений из кода BSL.
- Tools: `find_references`, `get_register_links`, `find_callers`, `get_dependency_graph`, `diff_configs`.
- **Критерий:** «найди всё, что сломается при удалении реквизита Y справочника X».

### Этап 3. Live-данные (≈1–1.5 недели)
- Расширение `MCPConnector`: HTTP-сервис (query, validate, object, movements, balances, eventlog, metadata), JSON-сериализация ссылок (`{type, uuid, presentation}`), лимиты.
- Инструкция публикации (Apache/IIS/`ibsrv`) и установки расширения (`/LoadCfg -Extension`, `/UpdateDBCfg`).
- Клиент и tools раздела 3.3.
- **Критерий:** агент подбирает тестовый документ запросом и показывает его движения.

### Этап 4. Проверка доработок (≈1 неделя)
- Обёртки пакетного режима: `check_modules`, `check_config`, `refresh_index` (инкрементальная выгрузка).
- `run_tests` (YAxUnit как основной вариант), `snapshot_query`/`compare_snapshot`.
- `eval_code` под флагом.
- **Критерий:** цикл «правка модуля → синтакс-контроль → проведение тестового документа → сравнение движений» проходит через MCP.

### Этап 5. Зрелость (≈1 неделя)
- Resources и Prompts; несколько баз в одном конфиге.
- Переход на tree-sitter-bsl для точного анализа вызовов.
- Документация, `CLAUDE.md`/skill с рекомендуемым workflow для агента, упаковка (`uvx mcp-1c`), CI.

## 8. Риски

| Риск | Митигирование |
|---|---|
| Большие конфигурации (ЕРП: >10k объектов, ГБ кода) | Инкрементальная индексация, FTS, пагинация ответов, краткие представления по умолчанию |
| Переполнение контекста агента | Жёсткие лимиты строк/символов, режимы `brief/full` |
| Опасные действия на базе | Read-only пользователь, флаг test-окружения, безопасный режим, аудит |
| Различия форматов выгрузки (версии платформы, EDT) | Абстракция парсера, фикстуры на обоих форматах |
| Лицензии 1С при пакетном запуске конфигуратора | Кэширование результатов, `ibcmd` где возможно |

## 9. Открытые вопросы к заказчику

1. ОС и версия платформы? Файловая или серверная база?
2. Конфигуратор или EDT (формат исходников)?
3. Какая конфигурация (УТ/ERP/БП/самописная)? Есть ли БСП?
4. Можно ли устанавливать расширение и публиковать HTTP-сервис на тестовой базе?
5. Какой фреймворк тестов используется (YAxUnit, Vanessa-ADD, нет)?
6. Нужен ли `eval_code` (выполнение произвольного кода) вообще?
